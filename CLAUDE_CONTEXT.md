# AI Data Migration Agent - Comprehensive Project Context

This document provides complete context for Claude (or any other AI/Developer) to understand the architecture, purpose, history, and roadmap of the **AI Data Migration Agent** project. 

Use this document to plan future architectural improvements, fix bugs, and understand the core design philosophies of the codebase.

---

## 1. Project Purpose & Philosophy
The **AI Data Migration Agent** is an intelligent ETL (Extract, Transform, Load) tool. Instead of writing hardcoded Pandas scripts to clean messy data, the user provides a source (e.g., CSV, Postgres) and a target. 

**The Core Philosophy:**
LLMs are great at analyzing messy data and writing rules, but they are terrible at executing code securely and deterministically at scale. Therefore, this project completely separates **Planning** from **Execution**. 
1. The AI acts only as an analyst, outputting a strict JSON plan using a custom Domain Specific Language (DSL).
2. The Python backend acts as the deterministic execution engine, applying those DSL steps securely using Pandas. 
*No `eval()` and no raw SQL generated by the LLM is ever executed on the database.*

---

## 2. Architecture Breakdown

The project uses a modular design pattern:

- **UI Layer (`app.py`)**: Built with Streamlit. Handles user file uploads, database connector configurations (Postgres, MongoDB, DuckDB), and visualizes the migration workflow (Logs, Previews).
- **Orchestration Layer (`graph.py`)**: Built with LangGraph. It models the migration pipeline as a StateGraph: `request_intake` → `schema_discovery` → `data_profiler` → `transformation_planner` → `migration_executor` → `reconciler` → `reporter`.
- **AI Agents (`agents/`)**: 
  - `migration_analyst.py` / `transformation_planner.py`: Profiles the data (unique counts, missing percentages) and prompts an LLM (Gemini or Groq) to output a JSON array of DSL transformations.
- **DSL Execution Engine (`etl/dsl_engine.py` & `etl/dsl_handlers_extended.py`)**: The crown jewel of the backend. It parses the LLM's JSON payload and maps actions like `parse_currency` or `fill_missing` to strict, pre-tested Python Pandas functions.
- **Connectors (`connectors/`)**: Abstracted classes (`BaseConnector`) handling connection pooling, schema reading, and data writing (`to_sql`) for various targets.

## 3. The Custom DSL Protocol

The AI is restricted to scheduling operations from a predefined catalog of actions. 
Examples of DSL actions:
- **Cleansing**: `fill_missing`, `drop_missing_rows`
- **Typing**: `cast_type` (int64, float64, str, datetime, bool, category)
- **Parsing**: `parse_currency`, `parse_datetime`, `parse_percentage`
- **Deduplication**: `remove_duplicates`, `keep_latest_duplicate`
- **Strings**: `normalize_case`, `strip_special_characters`
- **Columns**: `rename_column`, `drop_column`, `merge_columns`

**Strict DSL Rules the AI must follow:**
- Must provide `confidence` scores.
- When using `fill_missing`, it must provide `strategy` (e.g., median, constant) or a specific `value`.
- When using `cast_type`, it must provide `target_type`.

## 4. Recent Fixes & Critical Code Learnings

We recently ran extensive benchmarks using messy real-world datasets. Here is what we fixed and learned about the system's behavior:

### A. The Resilience of the Backend (A Massive Success)
We learned that the DSL Engine is incredibly resilient to LLM hallucinations. If an LLM schedules a mathematically impossible action (e.g., casting a column with `NaN` values to standard Pandas `int64`), or forgets a required argument (e.g., scheduling `keep_latest_duplicate` without providing the `timestamp_column`), **the application does not crash**. The DSL Engine traps the exception, logs the step as `Failed` in the UI, skips the broken step, and flawlessly executes the remainder of the pipeline.

### B. Recent Bug Fixes (Already Implemented)
- **Pandas Boolean String Gotcha**: Fixed a bug in `dsl_engine.py` where calling `.astype(bool)` on the strings `"False"` and `"True"` resulted in `True` for everything. It now explicitly maps `"False"` and `"0"` to python boolean objects before casting.
- **Percentage Parsing**: Fixed `parse_percentage` in `dsl_handlers_extended.py` to correctly divide by `100.0` (e.g., `84%` -> `0.84`) after stripping the `%` symbol.

### C. LLM Model Discrepancies
- **Gemini-2.5-Flash** performs exceptionally well. It is highly observant, automatically scheduling deep parsing (currency, datetimes) and chaining 12-17 transformations successfully.
- **Groq (Llama-3.3-70b)** is much "lazier". In tests, it ignored messy date formats (`Jan 5 2023`), ignored inconsistent casing (`ELECTRONICS` vs `electronic`), and only scheduled the exact transformations explicitly requested in the user prompt (doing 6 steps instead of Gemini's 12). 

### D. LLM Sequencing Traps
The AI frequently falls into "Sequencing Traps":
- Scheduling `cast_type: int64` *before* `fill_missing`. (Pandas standard integers cannot hold `NaN`).
- Scheduling `parse_currency` *after* `cast_type: float64` (resulting in failure because strings like `300$` can't be cast to float before being stripped).
*Note: The backend catches these and skips them safely, but ideally the AI prompts should be improved to warn the LLM about strict operation sequencing.*

## 5. Roadmap for Production Readiness (Claude's Next Tasks)

While the isolated DSL execution engine is solid, the application requires several major architectural upgrades to be considered "Enterprise Production Ready". Claude should focus on implementing the following:

### Phase 1: Scalability (The Memory Bottleneck)
Currently, `app.py` and the connectors load the entire dataset into a Pandas DataFrame (`pd.read_csv()`). A 5GB CSV with 10M rows will cause a fatal Out Of Memory (OOM) error.
**Goal:** Implement chunking (`pd.read_csv(chunksize=X)`). Alternatively, replace Pandas in the DSL Engine with **Polars** or **DuckDB** for out-of-core, multithreaded processing over massive datasets.

### Phase 2: Transaction Management & Rollbacks
Currently, data is pushed using `df.to_sql(if_exists="replace")`. If a migration crashes midway through, the database is left in a corrupted state.
**Goal:** Implement strict DB transactions (Begin/Commit/Rollback). Move towards **Idempotent Upserts** so migrations can be safely resumed without duplicating data.

### Phase 3: Strict Output Validation (Data Contracts)
Currently, whatever exits the DSL pipeline goes straight to the database. If the LLM misses an outlier, bad data enters production.
**Goal:** Integrate **Great Expectations** or **Pandera**. Before calling `.to_sql()`, enforce a strict schema contract (e.g., "Age must be > 0", "Emails must contain @"). Fail the pipeline securely if the contract is breached.

### Phase 4: Eradicating Regex Parsing
Currently, we extract the JSON DSL from the LLM's raw response using custom regex. This is brittle.
**Goal:** Refactor the LangGraph AI agents to use strict **Structured Outputs** (via `Instructor` or native Gemini JSON Schema capabilities) guaranteeing that the LLM response is mathematically valid JSON.

### Phase 5: CI/CD & Observability
**Goal:** Add a GitHub Actions pipeline to automate the `pytest` suite. Implement centralized logging (JSON logs) to track LLM token usage, failure rates, and execution latency.
